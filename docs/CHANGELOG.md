## [0.8.2] - 2026-10-06

### Added

- **Confirmed Account Deletion**: Account deletion is now a two-step, mailbox-confirmed flow. `DeleteAccountDialog` initiates deletion and never performs it; nothing is deleted at request time. Confirmation is blocked for an unverified address and says why. `DeletionPendingNotice` leads with the fact that the account is intact. Mailbox control is treated as distinct from fresh authentication, which the UI states explicitly, because a link in an old inbox is not proof that the person asking is present. Frontend: `DeleteAccountDialog`, `DeletionPendingNotice`, `EmailVerificationCard` (also used to change a verified address), `frontend/lib/api/account.ts` (per-request CSRF cookie). Backend: `app/core/account_lifecycle.py`, migration `v0_8_3_account_lifecycle`. Docs: `docs/EMAIL_SETUP.md`.
- **Native S3 / S3-Compatible Storage Backend**: New `app/core/s3_service.py` (boto3) provides an in-container storage backend alongside rclone, for the backup retention rotation, the shared cross-instance cover cache, and the feedback screenshot archive. `S3_BACKEND=auto|rclone|s3` selects the backend, and `auto` prefers rclone when a remote already exists. Works against AWS S3, MinIO, Cloudflare R2, Wasabi, Backblaze B2 and Oracle Cloud Object Storage; leaving every value blank runs fully local, with each role degrading to a no-op. Server-side encryption via `S3_SSE`. **Behaviour change:** the containers no longer shell out to rclone or mount `rclone.conf`, because handing a plaintext credential file to the process that parses untrusted input was the risk; host-side backup scripts still use your existing rclone install, unchanged. `RCLONE_REMOTE_ARCHIVE` and `RCLONE_FEEDBACK_REMOTE` are deprecated in favour of `S3_BUCKET_*`, and the app warns by name when one is set without a replacement.
- **Linked Open Data Entity Linking & Reconciliation Dashboard**: New `app/core/lod_linking_service.py` links catalog entities to external authorities, with background ETL in Celery. A new `/admin/lod` dashboard (**LOD Reconciliation**) shows linking metrics, batch controls and a live audit-log stream, and appears in the Settings and Content admin pages. Manifestation detail gains a semantic-links panel. Gated by `ENABLE_LOD_LINKING` (default on); `GEONAMES_USERNAME` enables GeoNames linking. See `docs/OPERATIONS.md`.
- **Enforced Container Image Size Gate**: `scripts/build_docker_images.sh` now fails the build when the backend image exceeds the budget in `deploy/image-size-budget.txt`, and the failure output names the largest individual packages so the cause is identifiable without a second multi-minute build. The size target used to be `<500 MB` of prose in a spec — prose cannot fail, so it went unmet through an entire release (1019.2 MB → 826.7 MB) with nothing breaking. A budget pointing at a number nothing can reach is worse than no budget, because it only trains people to disable it, so the figure is now **650,000,000 bytes** against a recorded measurement of **635,350,015 bytes (605.8 MiB)**. `MAX_BYTES` and `MEASURED_BYTES` are the single source of truth, and `scripts/validate_release.py --image-size-only` (also `make validate-release`) fails if `docs/RELEASE_PROCESS.md` quotes anything else, so the build gate and the release plan cannot drift apart — the exact way the previous requirement was missed. `make validate-image-size IMAGE=<tag>` checks an image that was not built locally. A budget file that cannot be parsed, or that records a measurement already above its own ceiling, fails the build rather than being read as "no limit". A new `image-size-gate` CI job builds the backend image and runs the same gate on `main`, `release/*` and `hotfix/*`, because `deploy.yml` publishes with `push: true` and buildx leaves no local image for a local-only check to inspect. It is deliberately **not** run on feature-branch PRs: it builds a Docker image, which costs real runner minutes, and the size it measures is a property of the branch rather than of the change under review. Feature-branch PRs still get the budget enforced for free, via `scripts/validate_release.py --image-size-only`, which checks that the release plan and the budget agree without building anything.
- **`scripts/phash_cover.py`**: Prints the perceptual hash of cover images for `IQOQO_KNOWN_JUNK_PHASHES`. `--check` reports whether an image is currently blocked and exits non-zero if it is not, which is how an operator verifies that hashes stored before the `ImageHash` removal still resolve.
- **Perceptual Hash Without numpy/scipy**: New `app/utils/phash.py` computes the pHash on Pillow and a precomputed DCT cosine matrix, replacing `imagehash.phash` — one function call that pulled in `scipy` (111 MB), `numpy` (57 MB) and `PyWavelets` (9 MB), **178 MB or 20% of the production image**. The algorithm is unchanged, so stored hashes keep matching: the result is byte-identical to `imagehash` across a 55-image corpus of artwork, placeholders and edge cases, and across 3000 randomised images. The one exception is documented rather than hidden — for mathematically symmetric input whose DCT block has coefficients *exactly* tied at the median, `imagehash`'s answer was decided by scipy's float64 rounding (~1e-16 relative) and is not reproducible by any independent implementation; this implementation returns the exact result, and `KNOWN_DIVERGENCES` in `tests/test_phash.py` pins the scope so it cannot widen unnoticed. Effect if a stale hash of such an image misses: one placeholder cover is displayed where a real one was expected — no data loss. Malformed entries in `IQOQO_KNOWN_JUNK_PHASHES` are now reported and ignored rather than silently reinterpreted; `imagehash.hex_to_hash` inferred the hash shape from the string's own length, so a short value quietly dropped its high bits.
- **Deterministic Duplicate Classification (no inference required)**: Candidate pairs are now classified before any inference: a shared edition identifier (`isbn13`/`ean`/`upc`/`barcode`) or an identical normalized title corroborated by a shared creator is accepted outright, and a shared creator whose title similarity falls below the floor is rejected as same-author noise. Only the remaining grey zone can reach a model, and only when the operator asks for it. A new `--engine heuristic|llama` flag (CLI) and `engine` field (scan endpoint) defaults to `heuristic`, so **a scan no longer requires a running Ollama instance** — which also removes a GPU dependency from containerized deployments. The Ollama health pre-check is now a prerequisite of the `llama` engine only. Measured on a production clone (2001 Works, 2058 Manifestations): 658 candidate pairs resolved into 40 queued, 144 auto-rejected, and 474 left explicitly undecided, with zero inference calls, in seconds instead of the 1–6 hours the previous path would have needed at 9–45 s per pair.
- **Candidate Provenance (`resolution_source`)**: New `duplicate_candidates.resolution_source` column (`heuristic` or `llama`), with `confidence` made nullable. A classifier verdict is categorical rather than probabilistic, so the review UI can label it differently from a model verdict instead of presenting `1.0` (shared identifier) alongside `0.99` (model confidence) as if they meant the same thing. Migration `v0_8_2_duplicate_provenance` backfills existing rows from the presence of an LLM rationale.
- **Shared Admin Sidebar**: The administrative navigation was duplicated across four admin pages and the copies had already drifted — the groups and duplicates pages were missing "User Requests" and "LOD Reconciliation" and labelled the API section "API Keys" where the settings and content pages said "API Integrations", so a custodian's navigation depended on which admin page they landed on. The item list and its permission gating now live once in `frontend/components/admin/admin-sidebar.tsx`, which reads the viewer's own profile, and all four pages render it.

The manual merge endpoint and the duplicate-review queue now execute the same re-pointing logic, so the two cannot drift apart. A coverage test reflects the SQLAlchemy metadata for every foreign key targeting `works.id`/`expressions.id`/`manifestations.id` and fails, naming the offending `(table, column)`, if a referencing column is added without a map entry or a justified exclusion. Runs under `make test-merge-integrity-pg` against a real PostgreSQL instance, because SQLite does not enforce foreign keys and therefore cannot see this class of defect.
- **`make test-merge-integrity-pg`**: Runs the FRBR merge coverage, integrity, and duplicate-detection suites against a throwaway database inside the isolated E2E PostgreSQL service. The database is created and dropped by the target, so no default, preview, or production stack is touched.
- **FRBR Duplicate Detection Service (C15)**: New `app/core/duplicate_service.py` performing heuristic candidate screening (normalized title, title prefix/suffix, sort title, creator overlap, and EAN/UPC/barcode blocking keys) followed by pairwise scoring against a local Ollama model. Adds self-describing `describe_work()`/`describe_manifestation()` payload builders, a `POST {OLLAMA_URL}/api/chat` JSON-mode client with a health pre-check, and a two-tier `run_detection()` pipeline. New env var `OLLAMA_DEDUPE_MODEL` (default `llama3:latest`).
- **Atomic FRBR Entity Merge**: `merge_work()` re-parents child Expressions, reconciles Work contributions and expansion links, and records an `EntityAuditLog` entry. `merge_manifestation()` re-parents child Items, consolidates contributions, and keeps ISBNs strictly on the Manifestation tier — the primary wins, a source ISBN the primary lacks is adopted, and a conflicting ISBN is preserved as a list in `meta["alternate_isbn13"]` (same pattern for `meta["alternate_barcodes"]`). Both re-point **every** table that references the entity onto the survivor — 14 ref-points for Works and 10 for Manifestations (13 and 9 real foreign keys, plus the polymorphic `SemanticLink` entry each), covering `ON DELETE CASCADE` links (which would otherwise silently destroy user data) as well as `SET NULL` links (which would otherwise be orphaned) — collapsing onto the survivor where a natural-key unique constraint would collide. - **Duplicate Review Admin API**: Four new endpoints on `admin_bp` under `/api/v1/admin/duplicates` — `GET /` (paginated pending-candidate queue with tier/status/confidence filtering), `POST /scan` (trigger a detection run), `POST /<id>/dismiss` (mark a false positive), and `POST /<id>/merge` (execute a transactional merge for a chosen primary). - **Frontend API Client**: New `DuplicateCandidate`, `DuplicateWorkSide`, and `DuplicateManifestationSide` types (a discriminated union on `tier`, so the comparison table needs no casts) plus `getDuplicateCandidates()`, `runDuplicateScan()`, `mergeDuplicateCandidate()`, and `dismissDuplicateCandidate()` in `frontend/lib/api/admin.ts`.
- **myKG Agent Harness Reliability — opencode v2 CLI contract**: The daemon was passing v1-only flags (`--pure`, `--variant`) that the v2 CLI no longer accepts, and a model variant was appended in a way that could duplicate an already-present one. The variant is now rendered as a `#` suffix, replacing rather than repeating. The CLI is invoked with `--standalone` so no background `serve --service` process is spawned — that orphan was the cause of an intermittent 100%-CPU spin that hung tasks until they hit their timeout. stdout/stderr are captured through temp files rather than pipes, because opencode's internal IPC writes to stdout immediately after its `init` handshake and `capture_output=True` filled the pipe buffer and deadlocked the parent on EOF *after* the client had already exited. The runtime store is persisted so opencode's 48-migration schema bootstrap runs once rather than per task, and the probe waits for egress-proxy health (the sandbox agent starts with `--no-deps` and therefore bypasses compose's `service_healthy` gate). A bats guard asserts the daemon never passes v1-only flags, so the regression cannot silently return.
- **myKG Per-Model Variant Degradation**: The fixed effort→variant map has been replaced with ordered preference lists that always terminate at "no variant". The ladder is walked only on a *variant-unavailable* rejection; an unrelated failure is attempted exactly once, so a genuine error is not disguised as three different variant attempts.
- **myKG Credential Delivery**: Each provider is mapped to its catalogue-declared environment variable and the key is read from the read-only auth mount, then injected into the child process environment — so the key is delivered **without ever appearing in the argument vector** (where it would be visible in `ps`). A pre-set environment variable takes precedence over the mount, and an absent or malformed secret is tolerated with a warning naming the real consequence rather than fabricating a key or crashing the daemon.
- **myKG Retry Budget**: A single transient failure previously wrote a terminal `.error` envelope that `is_task_done()` never overwrote, so one bad task silently dropped that extraction from the graph *while the run still reported success*. Envelopes now carry an `attempts` counter and are rewritten while budget remains (`MYKG_MAX_TASK_ATTEMPTS`, default 3); the terminal envelope freezes once the budget is spent, so a permanently broken model cannot churn forever. The completion gate is budget-aware — a transient failure is not terminal, but a real answer always wins. Legacy envelopes with no `attempts` field are treated as a single attempt so pre-existing failures get the benefit of the budget instead of being stranded, and a stale failure marker is removed when a task is subsequently answered.
- **myKG Queue Drain**: `mykg_sync.sh` now waits for unfinished tasks to reach zero before its teardown trap removes the daemon — the teardown was previously racing the last tasks, which is exactly when the drain is needed. The wait is bounded (`MYKG_DRAIN_TIMEOUT`, default 900 s) and a timeout is reported as a backlog rather than a failed run; the wait is skipped when no daemon is running. Completions are reported alongside the outstanding count, and a stall is called out explicitly after 60 s with no completions, because an unchanged pending count is otherwise indistinguishable from progress. Daemon concurrency is raised above one so a single slow task cannot block the queue.
- **`make mykg-retry` — re-queue failed agent tasks**: Clears the failure markers for tasks that can actually be retried, **quarantining rather than deleting** them, and classifies before acting: markers are deliberately left on already-answered and payload-less tasks, and the two groups are reported separately. Supports an inspection mode and a named session, refuses to silently fall back to the latest session when given a bogus name, and follows a symlinked session store. `ARGS="--dry-run"` inspects without changing state.
- **`make mykg-probe` — sandboxed model probe**: Exercises real model calls **without touching mykg session state**, because every failed task writes a terminal `.error` envelope — `make mykg-update` is the wrong place to discover that a model is broken, because discovering it there poisons real extraction work. The probe uses the daemon's own credential path so it cannot drift from production behaviour, and includes a host control run so a failure is attributable to the environment rather than the model. Capture-hang diagnostics are collected from *inside* the container, since `compose run --rm` otherwise destroys the only evidence. A bats guard asserts the probe never references session inbox/outbox paths or the extraction runner. **Makes real (billed) API calls.**
- **myKG Egress Allowlist Tightened**: The `models.dev` egress rule added during diagnosis has been reverted, and the allowlist now documents why the host is deliberately absent — the catalogue is served from a permitted host, so the extra rule was unjustified egress.

### Security

The fixes below were released as security-relevant. Each entry names the concrete
failure mode, because "hardened the X" is not something a reader can verify.

- **Logging Out Never Revoked the Token** ⚠️ **Fix — security relevant.** `POST /api/auth/logout` in the browser resolved to the Next.js route handler at `frontend/app/api/auth/logout/route.ts`, which **deleted the session cookie and did nothing else**. Next route handlers take precedence over the `/api/:path*` rewrite in `next.config.ts`, and that file sits at exactly the rewritten path, so Flask's `/api/auth/logout` — the code that adds the token's `jti` to the blocklist — was unreachable from any browser request. The JWT in the cookie therefore stayed cryptographically valid until it expired: logout cleared the local cookie and redirected to `/login` while the token kept working, so any copy of it (a proxy log, a shared machine, an exfiltrated cookie) would still authenticate after sign-out. Two tests covering token revocation pass, because they call the Flask endpoint directly. The handler now forwards the token to Flask as a `Bearer` header before clearing the cookie. A failure to revoke is swallowed deliberately — keeping the cookie would leave the user signed in against an explicit request, which is worse than a token the backend failed to revoke.
- **Login Timed Differently Depending on Whether an Account Existed** ⚠️ **Fix.** `POST /api/auth/login` evaluated `if not user or not user.check_password(password)`, so an unknown email returned **without ever running the password hash**: measured **0.00 ms against 90.40 ms** for a registered address with a wrong password, on identical code. The KDF is scrypt, which dominates the request, so that gap enumerates every registered address far more reliably than the generic `"Invalid credentials"` body hides it — and the endpoint's own docstring claimed the failure response does not reveal whether an account exists. Confirmed by measurement: `manifestation_<id>_cover.jpg` remained after every rejected upload, publicly served from `/static/covers/`, referenced by no row, and never garbage-collected. Cleanup is now shared by the 404 path and the exception path. The module's own docstring named this exact defect, and a test claimed to cover it — but it passed raw `bytes` instead of a stream, so Werkzeug parsed it as an ordinary form field and the endpoint rejected the request before saving anything; it also inspected `app.config["COVER_UPLOAD_DIR"]`, which is unset, rather than the directory the code writes to. It could not have failed.
- **Both Forbidden-Suppression Safeguards Could Be Bypassed** ⚠️ **Fix.** `tests/test_lint_safeguards.py` guards against `too-many-return-statements` and `broad-exception-caught` being disabled in `app/`, `scripts/` and `tests/`. Both patterns anchored the forbidden name to the start of the pylint code list, but pylint accepts those codes in **any order** — so appending the forbidden name to an unrelated directive suppressed it just as effectively while matching nothing. Measured six escapes, including the plain `# pylint: disable=broad-exception-caught, too-many-return-statements`, the same with no space after the comma, no space after the colon, spaces around `=`, an uppercased message name, and an indented directive inside a function. Both now parse the whole list and test membership, case-insensitively. A safeguard whose own pattern can be evaded is worse than none: it is reported as working while the code it excludes gets in. Nineteen tests cover it, six confirmed to fail against the old pattern, including seven lines that must *not* be flagged — the code inside a string literal, after `enable=`, and as a longer name — so the guard does not cry wolf, plus one asserting files were actually scanned so it cannot pass vacuously.
- **A Type Change Did Not Reach Items, and the Stale Metadata Escaped Into Exports** ⚠️ **Recorded, not fixed — see below.** `update_frbr_entity_type` walks Work → Expression → Manifestation, syncing each entity's `type`/`format`/`Format` and degrading a carrier that no longer applies to the new type's `unknown_*` placeholder. It does not descend into Items. Reclassifying an Expression from `text` to `music` therefore leaves `manifestation.format: unknown_audio` beside `item.meta: {type: text, format: book}`. `Item` has no `format` column, so the Manifestation is the structural authority and the item's copy — written by ingest — is a denormalised duplicate. It is not harmless: `DataManager._export_item_row` serialises `"meta": item.meta` verbatim, so a reclassified title is exported still claiming it is a book. The UI is unaffected only because `item-sidebar.tsx` reads the manifestation's copy first. No fix ships with this release: propagating means writing into a free-form dict that also holds user-annotated fields, for every Item under the changed Manifestation, in the same transaction as the type change — and not consulting the item copy at all is the other option. Both are production behaviour changes with their own trade-offs. A characterisation test pins the current boundary and asserts the two copies disagree, so this cannot quietly become expected behaviour.
- **Login Timed Differently Depending on Whether an Account Existed** ⚠️ **Fix.** `POST /api/auth/login` evaluated `if not user or not user.check_password(password)`, so an unknown email returned **without ever running the password hash**: measured **0.00 ms against 90.40 ms** for a registered address with a wrong password, on identical code. The KDF is scrypt, which dominates the request, so that gap enumerates every registered address far more reliably than the generic `"Invalid credentials"` body hides it — and the endpoint's own docstring claimed the failure response does not reveal whether an account exists. A second shape leaked identically: `password_hash` is nullable and permitted to be NULL for Google-linked accounts, and `check_password` returned `False` immediately for those, making them exactly as fast as an address that does not exist. Login now always performs a password verification, comparing against a throwaway hash of a fresh per-process random value when there is nothing to check. The measured gap is **−0.28 ms**, and a Google-only account is within **0.38 ms** of an unknown one. Rate limiting (5/minute) and the 8-character minimum were unaffected — neither mitigates a timing oracle. A suspended account still returns `403` where everything else returns `401`; that remains a deliberate product decision.
- **An Expression Escalation Rendered as Unclickable Text** ⚠️ **Fix**: both escalation link generators guarded on `expression_id && work_id`, but `create_escalation_request` writes only one target column and the database constraint allows at most one — so a real Expression escalation has `work_id` **NULL** and the guard never matched. Every Expression escalation fell through to `null`, and since the escalation list renders plain text instead of a link when there is no href, the person who filed it could no longer reach the entity they were escalating about. The custodian view had the same defect. Both now key on `expression_id` alone. The two pre-existing tests covered only the `work_id`-present shape, which the API never produces — they were rewritten, not deleted.
- **The Lending Test-Reset Helper Now Requires a Shared Secret** ⚠️ **Hardening, not a live vulnerability.** `POST /api/lending/test/reset` resets every lent Item and deletes every loan request, and it carries no authentication of its own. Its only gate is the `TESTING` flag, which is set solely through `create_app(config_override=...)` — no deployment path can set it today. The guard exists so that a *future* mistake in how `TESTING` is configured would no longer, by itself, expose an unauthenticated state-mutating endpoint. Requests must now present a matching `X-E2E-Reset-Secret`, compared in constant time; when `E2E_RESET_SECRET` is unset the endpoint refuses every request rather than falling open. Separately: the E2E lending spec was calling this endpoint and **discarding the response**, so the 403 it has always been returning was invisible — it now asserts the status. That reset was not in fact clearing lending state between runs.
- **Restoring Covers Could Write the Wrong Cover Onto the Wrong Record** ⚠️ **Fix**: `scripts/restore_covers.py` matched each archive entry with `filter_by(isbn13=...).first()`. An entry without an ISBN became `filter_by(isbn13=None)`, matching **every** ISBN-less manifestation, and `.first()` returned one of them by storage order — so the archive's cover was written onto an arbitrary record. Vinyl, board games and puzzles routinely have no ISBN. Restoration is also the moment a wrong cover is least likely to be noticed, since the operator has just restored the database and expects the covers to match it. Entries are now resolved strongest-identifier-first and only when present, accepted only when they narrow to exactly one row, and refused with a warning when two rows share a value rather than guessed at. A UPC that identifies a single record still restores — the defect was widening a query with an absent field, not an insufficient identifier.
- **Cover Maintenance Scripts Issued ~7.5 Queries Per Catalog Row** ⚠️ **Fix**: `fetch_covers.py`, `retry_missing_covers.py` and `generate_ai_covers.py` each walk `expression.work` for every manifestation in a batch. On a lazy graph that costs about 7.5 SELECTs per row, because `Work` pulls in semantic links, work parts and contributions — measured at **38 SELECTs for 5 rows**, growing with the batch. All three now eager-load the chain, making the count constant at 10 regardless of batch size.
- **A Corrupt Cover Archive Reported a Successful Import** ⚠️ **Fix**: `scripts/import_covers.sh` had no `set -e`, so a truncated or corrupt archive made `tar` fail while the script continued regardless — then ran the cover-rebinding step against a **half-extracted** directory and printed `✅ Import complete!`. Covers were silently lost. The script now uses `set -euo pipefail`, matching the nine other scripts that already do, validates the archive on the host with `tar -tzf` before the container is touched at all, and checks the extraction step explicitly so the message names what happened and confirms rebinding did not run. Two of its own bats tests were passing for the wrong reason: they built the test archive with `touch`, producing a zero-byte file that is not a gzip archive, so with nothing validating the input they asserted nothing about the success path.
- **A Catalog Backup Import Could Silently Attach Records to the Wrong Parent** ⚠️ **Fix**: `import_data()` remaps the ids in a backup as it inserts, but every lookup fell back to **the raw id from the file** when the mapping was missing. Because `work_id`, `expression_id` and `manifestation_id` are real foreign keys, a backup missing a referenced row would either fail at commit — far from the entry at fault — or, if a row happened to already exist at that id, quietly attach the record to an **unrelated** Work and report success. That is silent catalog corruption, and it is now refused with a message naming the entity, the offending reference, and the remedy. References are satisfied only by the map built earlier in the same import, never by coincidence.
- **Invalid Enum Values and Dates in a Backup Reached the Database** ⚠️ **Fix**: a backup carrying `status: "to_read"` (rather than `want_to_read`) or an unparseable `publication_date` was rejected by a CHECK or NOT NULL constraint with a driver error that never named the offending field. Values are now validated before insert, with the valid set printed in the error. A blank Work title is likewise caught by name. Owner resolution is unchanged and still runs before any catalog insert, so a rejected payload leaves the collection exactly as it was.
- **A Swallowed Error in the Security Migration Could Delete a User's Whole Collection** ⚠️ **Fix**: `v0_8_1_security_constraints` decides whether to **delete** or merely **disable** the transitional legacy system user, based on whether that user still owns items. It caught `Exception` and defaulted to "owns nothing" — the destructive direction, since `Item.owner_id` is `ON DELETE CASCADE`. A transient failure (dropped connection, permission error, typo) would therefore have deleted the `auth.users` row and taken the collection with it. The migration's own `check_user_auth_method` guard does not save the data: it counts rows in `auth.users`, and the deleted row is no longer there, so the migration would succeed. The probe now fails closed with an actionable message, matching the pattern the same migration already uses for its other guard — a false negative merely disables an account, which is reversible. The swallow had also been concealing a gap in two of the migration's own tests, which built `users` and `container_aggregations` but never `items`, so the probe was failing on a missing table and being absorbed; those fixtures are now complete.
- **Three Indexes Existed Under Names the Models Cannot Generate** ⚠️ **Fix**: new migration `v0_8_2_fk_index_names` renames them. `index=True` on a *schema-qualified* column makes SQLAlchemy produce a **schema-prefixed** name — `inventory.items.manifestation_id` yields `ix_inventory_items_manifestation_id`, not `ix_items_manifestation_id` — but the migrations hardcoded the schema-less names, which are correct on SQLite and wrong on PostgreSQL. The consequence: `flask db revision --autogenerate` against a migrated database proposed renaming **all three** indexes on `inventory.items`, including the two that were already correct, so autogenerate could never converge — each run emitted a migration undoing the previous one. Two of the three were introduced by `v0_8_2_fk_indexes_and_quantity`; the third (`instance_settings`) dates back to the baseline and survived that table's later move from `catalog` to `config`. All three are invisible to the SQLite-backed suite, which is why they persisted. A new PostgreSQL-gated test asserts that *every* model-declared index exists under exactly its generated name, so the class is covered rather than the three instances known today.
- **Admin Content Search Opened a Record Nobody Selected** ⚠️ **Fix**: the FRBR content editor auto-selected a manifestation whenever a search returned exactly one result. The search is a `%substring%` match (`app/api/admin.py:714`), so a half-typed query that happens to match one row — `dun` for *Dune*, or a prefix shared by one title — silently replaced the search UI with that row's editor. For a custodian, opening the wrong record to edit metadata is worse than one extra click, so selection is now always explicit. The result row is also a real `<button>` now: it was a `div` with an `onClick`, which made the results list unreachable by keyboard and left selection with no accessible path at all.
- **Shared Collection Links Silently Dropped Every Status But the First**: the collection page allows multi-select status filters, but the share dialog passed only `statuses[0]` — carrying a `// assuming single status for now` comment — so a link created from a view showing two statuses covered one of them. The dialog now sends the full list, and the shared-items endpoint accepts either a single status or a list, so existing links keep resolving. A malformed or empty status list now matches nothing rather than dropping the predicate and widening the link to the sharer's entire library.
- **Public Profiles Only Ever Showed the First 24 Items**: the profile page fetched `/public/u/<name>/items` with no pagination, but that endpoint paginates server-side (default 24, capped at 100). A collector with 500 public items had no route to the rest — the remainder was unreachable, not merely slow. The page now forwards the requested page and renders navigation that keeps the first and last pages reachable for long ranges, clamping malformed or hostile `?page=` values before they reach the API. Its `getItems` and translation fetches also run concurrently with the profile fetch rather than after it.
- **Public Profile JSON-LD Advertised the Wrong Item Count**: `publicItemCount` was populated from the length of the single fetched page, so a profile with 500 public items published `"publicItemCount": 24` to search engines. It now uses the API's own total.
- **The Same Item Could Render as a Film in One Place and a Book in Another**: "is this a video?" was written out in eight different spellings across six components, and the lists had already drifted — `extended-metadata.tsx` counted `movie`, `unknown_video` and `cards` as video/game carriers while the other five did not, so an Item's badge, icon and metadata panel could disagree about what it was. All of them now use `frontend/lib/media-classification.ts` as the single source of truth. (The scanner's success card keeps its own lists deliberately: it maps a *scan result* to a picker label, which is a different concern from classifying a catalog Item.)
- **Landing Page Stats Strip Shifted the Layout Below It**: `GlobalStats` returned `null` while its fetch was in flight, so the strip occupied no height until the data landed and then appeared, pushing everything beneath it down — Cumulative Layout Shift on the landing page, above the fold. It now renders a placeholder grid reserving the same four card slots as the real render, via a new `Skeleton` primitive (the project had none). The placeholder is `aria-hidden`, since a screen reader announcing four empty cards mid-load is worse than announcing nothing.
- **Deleting a Manifestation Scanned the Whole Items Table**: `inventory.items.manifestation_id` is `ON DELETE CASCADE` but had no index, and PostgreSQL does not create one for a foreign key. `EXPLAIN` confirmed a sequential scan even with sequential scans disabled. The same applied to `catalog.reading_roadmaps.user_id`, a UUID column, which made the absence easy to miss. Both are now indexed (`ix_items_manifestation_id`, `ix_reading_roadmaps_user_id`) and the planner uses an index scan.
- **A Box Could Record Zero Components Without Complaint**: `container_aggregations.quantity` had a Python-side `default=1`, which applies on insert only — an update could still store `NULL`. The serializer then emitted `quantity or 1`, so a `NULL` was indistinguishable from a genuine `1` at the API boundary: a data-entry bug became invisible rather than caught. The column is now `NOT NULL` with a server-side default and a `quantity > 0` check, since a box containing none of a component is not a meaningful state to persist. Migration `v0_8_2_fk_indexes_and_quantity` refuses to run — before touching the table — if existing rows would violate the constraint, and on PostgreSQL the whole thing rolls back cleanly rather than failing midway through a rebuild.
- **An Inert Flag Suggested a Redefinition That Never Happened**: `loan_requests.__table_args__` carried `extend_existing=True`, implying the table was being redefined somewhere. Reproducing the exact configuration with and without the flag produced an identical model, and no migration uses it. Removed.
- **QR Label Print Executed Catalog Titles as Markup**: the print path in `PrintQrCodeDialog` builds an HTML string and hands it to `document.write()` in a new window, interpolating the Work title and the authors line **raw**. Titles are user-supplied catalog data, so a title such as `</div><script>…` would close the label element and execute script in the print window's origin — and a Work title is exactly the field a contributor can set to anything. All three interpolation sites now pass through a new `escapeHtml()` helper (`frontend/lib/html.ts`) whose docstring states the boundary it is for: raw-string templates only, never ordinary JSX, since React already escapes and double-encoding would mangle every label.
- **Admin User List Reported an Outage as an Empty Tenant**: `UserManagement` caught a failed `getUsers()` call with `console.error` only, then rendered its empty state — the literal text "No users found." A 500 or a dropped connection was therefore indistinguishable from a deployment with no users, and an administrator looking at a broken admin page could reasonably conclude every account had been deleted. Failures now raise a `sonner` toast and render a distinct destructive row naming the failure, and the message clears once a later fetch succeeds so a transient 503 does not leave a stale banner. A genuinely empty result still says "No users found."
- **Cover Text Overlay Existed in Two Copies**: `add_text_overlay_bytes()` and `add_text_overlay()` in `app/utils/images.py` were ~84% line-identical — the font fallback ladder, iterative shrink-to-fit, text wrapping, centring and stroke logic were copy-pasted between them, so a layout fix had to be made twice and a fix applied to only one copy produced covers that differed depending on which pipeline generated them. They now delegate the drawing to a single `_draw_text_overlay()`, leaving each wrapper owning only whether it reads bytes or a path and writes to a buffer or a file. Both public signatures and their failure modes are unchanged: a font or decode problem still yields an unbranded cover rather than a lost image, and a file already on disk is never left truncated. Verified pixel-identical across both wrappers, including for text long enough to trigger the shrink-to-fit path.
- **Outbound Requests Identified the Wrong Client Version**: three provider clients sent a hardcoded `User-Agent` — `musicbrainz.py` and `bgg.py` both claimed `iqoqo/0.3.0`, `covers.py` claimed `iqoqo/0.7.1`, against an actual version of **0.8.2**. BGG's API policy asks callers to identify themselves so operators can contact them, so a wrong version makes bug reports originating there unactionable. All three now interpolate `Config.VERSION`, matching the pattern `discogs.py` already used. A test scans every module in `app/utils/` for a hardcoded `User-Agent` version, so a fourth stale site cannot be added without failing CI.
- **Cover Metadata Extraction Discarded Valid JSON**: `_parse_json_response()` in `app/utils/vision.py` accepted only a bare or fenced JSON payload, so a local vision model that wrapped its answer in prose — "Here is the result: `{...}` hope that helps" — produced `None` and the extraction silently fell through to Tesseract, which reads pixels rather than meaning and so returned a worse answer with no error surfaced. It now uses `json.JSONDecoder().raw_decode()` to consume exactly one complete object, tolerating surrounding prose, trailing braces, and a model that emits more than one object. (The obvious `re.search(r"\{.*\}")` fix is wrong: it spans sibling objects and swallows trailing braces.) The Ollama vision timeout also rises from 30s to 90s by default — the same model needed **45.7s cold and 9.1s warm** on a real run, so the old ceiling discarded cold starts that would have succeeded. It is overridable via `OLLAMA_VISION_TIMEOUT`, because the correct value depends on the host.
- **DNS Resolution Leaked a Thread Per Lookup**: `_resolve_with_timeout()` in `app/utils/http_client.py` is the SSRF guard — `socket.getaddrinfo()` has no native timeout, so the lookup runs in a thread with a hard 5-second ceiling. But it built a **new** `ThreadPoolExecutor(max_workers=1)` for every call and then called `shutdown(wait=False)`, which releases the executor *object* while leaving the worker thread alive. A burst of requests — or a burst of *timeout* responses — therefore spawned one unkillable thread each, with nothing capping the total. That is the opposite of the starvation defense the function was written to provide: rather than losing a bounded number of workers, a sustained DNS stall could exhaust the process's thread budget and take the web tier with it. The pool is now a process-wide singleton (`_DNS_MAX_WORKERS = 8`) behind a bounded slot semaphore (`_DNS_MAX_SLOTS = 16`), so 41 sequential lookups cost 1 thread instead of 41, and a stalled resolver pins exactly 8 workers rather than growing without limit. **Exhaustion now fails closed** with `SSRFError`: resolving unchecked to preserve availability would have defeated the SSRF protection the function exists to provide. The abandoned future is cancelled rather than the pool torn down, since a thread already inside the C-level resolver cannot be interrupted.
- **FRBR Work Merge Preserved Wishlist Entries**: `merge_work()` did not re-point `UserWorkIntent.work_id`, which is `ON DELETE CASCADE`, so merging a Work a user had on their wishlist silently deleted the wishlist row. All 13 Work-referencing and 9 Manifestation-referencing columns are now re-pointed, collapsing onto the survivor where a natural-key unique constraint would otherwise collide.
- **FRBR Work Merge No Longer Crashes on Box Sets**: `_repoint_unique_child()` detected natural-key collisions with `select(model.id)`, but `WorkPart` has a composite primary key and no `id` column, so any merge involving an F15 box set or anthology raised `AttributeError` and failed outright.
- ⚠️ **BREAKING (silent data loss): Manual FRBR Merge Destroyed Referencing Rows**: `merge_frbr_entities()` — the *Relation Management → Merge* action in the FRBR editor, shipped in v0.8.1 — re-pointed only 2 of the 13 columns referencing a Work. Because eleven of the unhandled columns are `ON DELETE CASCADE`, deleting the source row silently destroyed the reader's **wishlist entries**, **box-set memberships** (`WorkPart`), **work expansions** (`WorkExpansionLink`), **container aggregations**, **social feedback**, **social notes**, and **escalation requests**. Measured on PostgreSQL 18: 8 of 9 referencing rows destroyed, against 0 for the duplicate-review path. The endpoint now runs the shared merge core and preserves all of them.
- ⚠️ **BREAKING (silent data loss): Manual FRBR Merge Dropped Unique Contributors**: the same function removed the source entity with an ORM `db.session.delete()`. `Work.contributions` is declared `cascade="all, delete-orphan"` with `lazy="selectin"`, and re-pointing a child by assigning its foreign-key column does not update the parent's already-loaded collection — so a contributor that existed *only* on the source was deleted rather than migrated, leaving the merged Work with two contributors where three were correct. The shared core now removes the source row with a Core-level `DELETE`, which bypasses ORM cascade processing, and the invariant is documented and tested.
- **Manual FRBR Merge Is Transactional and Audited Consistently**: `merge_frbr_entities()` had no rollback wrapper, so a mid-merge failure could leave a partially flushed session. It now locks both rows in ascending id order, rolls back on any failure, writes the tier-specific `change_type` (`merge_work` / `merge_expression` / `merge_manifestation`) so one query reconstructs every merge regardless of origin, records the per-table re-point counters, reconciles edition identifiers on Manifestation merges, and is rate limited. Its signature and API response shape are unchanged.
- **Duplicate Detection No Longer Requires a Language Model**: `POST /api/v1/admin/duplicates/scan` and `scripts/detect_duplicates.py` returned a hard 409/exit 2 when Ollama was unreachable, even though the two-stage pipeline could not realistically use it: a local 8B model takes **45.7 s cold and 9.1 s warm** per pair against a 15 s client timeout, and the scan runs synchronously inside a request whose gunicorn worker times out at 30 s — so a multi-pair scan could never complete regardless of the timeout. The deterministic classifier now resolves most pairs without inference, and the model is consulted only for the grey zone when explicitly requested. A pair sharing a conclusive identifier no longer pays for a call it did not need.
- **Duplicate Candidate Tests Are Valid on PostgreSQL**: `test_duplicate_detection.py` created `Item` and `EntityAuditLog` rows referencing random `uuid4()` owner and actor ids that exist in no user table. SQLite does not enforce foreign keys, so this was never exercised; PostgreSQL rejected every insert. Tests now create a real owning user, and the SQLite-only `PRAGMA foreign_keys` calls are now dialect-aware.
- **Duplicate Detection CLI Has Test Coverage**: `scripts/detect_duplicates.py` had no automated tests at all — its flags and exit codes were only ever verified by hand. Added coverage for engine selection, the default engine not probing Ollama, `--skip-health-check`, unknown-engine rejection, and the exit-2 prerequisite path.
- **Test Fixture No Longer Blocks on PostgreSQL Teardown**: the shared `app` fixture issued `drop_all()` while the test's session was still `idle in transaction` and holding row locks, so `DROP TABLE` blocked indefinitely on PostgreSQL. The session is now closed before DDL.
- **myKG Agent Failures Were Undiagnosable**: the harness recorded the CLI's own stderr on the subprocess failure path, but the generic exception handler in **both** harnesses (`opencode_daemon.py`, `agy_daemon.py`) reduced a failure to its class name — an envelope read `Unexpected error: ValueError`, which identifies nothing. Six tasks from a 2,710-chunk run burned the full retry budget in exactly that state, and the real cause (`Expecting ',' delimiter: line 1 column 13`) was only recoverable by grepping a 9 MB `run.log`, which defeats the purpose of recording failures at all. Failures now carry the exception message, and a bare exception (the common `json.loads` case, whose `str()` is empty) reports the deepest traceback frame as `file.py:line in function()`. Redaction is unchanged: the message passes through the existing `sanitize_error_text()` on write, so paths, environment variables and token-shaped strings are still stripped.
- **Duplicate Review Access Scoped to Custodians**: The duplicate review endpoints were gated on the `admin` role rather than a permission, and the sidebar entry was gated on `read:metadata` — a permission the *standard user* role also holds, so every logged-in user saw a Duplicate Review link that led to a 403. Listing now requires `read:metadata`; scan, dismiss, and merge require `write:metadata`, which the `contributor` role holds. The page itself now redirects non-custodians instead of relying on a hidden link.

- **Ontology Expansion**: Support for Video (Film, Series), Board Games, and Jigsaw Puzzles via FRBRoo `ManifestationContribution` (Studio/Distributor) and `ContainerAggregation` (Box Contents).
- **External API Integrations**: Integrated TMDB (The Movie Database), BGG (BoardGameGeek), Allegro (Retail), and UPCItemDB for robust barcode fallback resolution and rich metadata fetching.
- **Async Task Queue**: Implemented a `ThreadPoolExecutor` (`app/core/tasks.py`) for executing and polling LLM Vision cover metadata extractions asynchronously without blocking the UI.
- **UI Attributions**: Added `TmdbAttribution` and `BggAttribution` components to comply with external API Terms of Service.
- **Background Tasks**: Centralized APScheduler for recurring maintenance (e.g., daily automated backups).
- **Navigation UX**: Added "View in My Collection" button to manifestation details, allowing users to jump directly to their owned items.
- **Telemetry Hardening**: Refactored `LLMTelemetry` to handle high-concurrency event logging with non-blocking database indexes.
- **Scanner Fallbacks**: Added a `ManualEntryForm` UX to handle scenarios where barcode/ISBN lookups timeout or return no results.
- **Desktop Scanner UX**: `CameraCapture` now detects available media devices. If no rear camera is detected (e.g., Desktop), it automatically defaults to a clean Drag & Drop file uploader UI.

### Changed

- **Scheduler Gating**: Background tasks are now gated by `SCHEDULER_AUTOSTART` to prevent side effects in CLI and test environments.
- **Backup Script**: Isolated `sys.path` mutations to prevent environment pollution when the backup module is imported.

### Fixed

- **Manifestation Ownership**: Implemented `@optional_auth` decorator for `/manifestations` endpoints to correctly detect `user_owns` status for authenticated users.
- **Image Rotation**: Applied `PIL.ImageOps.exif_transpose` within the image processing pipeline to automatically fix the 90-degree rotation bug caused by smartphone EXIF metadata tags during cover uploads.

### Documentation

- **Backups**: Documented the Scheduled Backups system and environment configuration in `docs/ARCHITECTURE.md`.

### Database Migrations

- Introduced multi-schema architecture (`catalog`, `inventory`, `auth`).
- Added DB-level `CheckConstraint` to `ContainerAggregation` to ensure data integrity of board game components.

## [0.2.0] - 2026-04-03

### Added

- **Audio Support**: Full support for Vinyls, CDs, and Audiobooks via FRBRoo Event-Based Modeling.
- **Multiple Scans**: Added a secondary image upload system to manifestations (Disc, Inlay, Box, Back Cover).
- **Audio UI**: Item views now dynamically render `Tracklists`, `Matrix Numbers`, `Pressing IDs`, and `Labels` for supported media types.
- **Categorized Statuses**: Reorganized the item status dropdown into functional categories (Availability, Reading, Listening, Acquisition) for better collection management.
- **New Item Statuses**: Added `Damaged`, `Listening`, `Listened`, `Ordered`, and `Lost` to the canonical status list.
- **E2E Acquisition Tests**: New Playwright test suite covering Book, CD, and Vinyl ingestion via ISBN lookup, barcode scanning, and cover art analysis.

### Changed

- **Vision Waterfall**: Hardened exception handling to ensure robust fallback from Gemini to local backends (Ollama, Tesseract) during API or network failures.
- **UI Refinement**: Updated `ItemSidebar` to include the `MultiImageUploader` and categorized status selection.
- **Infrastructure**: Added `GALLERY_DIR` for storing secondary manifestation scans.

## [0.1.0] - 2026-03-28

### Added

- **Vision-based Metadata Extraction**: Added ability to extract `Title` and `Authors` from cover images via Gemini, Ollama (llava), or Tesseract OCR.
- **New Endpoints**: Added `POST /api/vision/extract` for handling cover image uploads (max 10MB) and extraction.
- **Full-Text Search**: Added PostgreSQL `TSVECTOR` columns (`fts_simple`) to `Work` and `Manifestation` for optimized searching.
- **LLM Permissions & Telemetry**: Introduced granular RBAC permissions (`LLM_GENERATE_COVER`, `LLM_GENERATE_METADATA`, `LLM_GENERATE_CLOUD`), a global `ALLOW_LLM` feature flag, and per-user telemetry tracking (duration/cost).
- **Manual Entry Extensions**: Added support for `ISBN` and `PublicationDate` when creating items manually.

### Changed

- **Proxy & CORS**: Updated `ProxyFix` to include `x_port=1` and enabled `supports_credentials=True` for OAuth sessions.
- **Code Formatting**: Updated Prettier configuration to use double quotes (`singleQuote: false`).
- **Dependencies**: Added `tesseract-ocr` system dependency to the Dockerfile.

## [0.0.7] - 2026-03-22

### Added

- **Owner-Scoped Dashboard Stats:** `GET /api/stats` now requires authentication and returns statistics scoped to the authenticated user's collection. FRBR entity counts (works, expressions, manifestations) use `DISTINCT` joins to avoid inflation when multiple items share the same manifestation.
- **`/api/config` Endpoint:** New public endpoint exposing runtime feature flags to the frontend (initially `FEDERATION_ENABLED`). Does not require authentication.
- **`unread` Item Status:** Added `unread` as a canonical item status to `ITEM_STATUSES`, enabling users to mark items as unread. Collection filter bar and sidebar now include an "Unread" filter option.
- **Manual Item Creation:** New `POST /api/items/manual` endpoint allowing users to add items by title/author/ISBN without scanning, backed by the `useAddManualItem` React Query mutation hook.
- **Federation Feature Flag:** Added `FEDERATION_ENABLED` environment variable. Federation-related UI (profile consent, federation tab on item detail) is now hidden behind this flag via `useAppConfig`.
- **`Makefile` `init` target:** Added `make init` for local dev bootstrap (creates venv, installs requirements, installs frontend node modules).

### Changed

- **Performance — Stats Query:** Replaced N+1 `COUNT` queries per status in `DataManager.get_stats()` with a single `GROUP BY Item.status` aggregate query, reducing DB round-trips from 7+ to 1.
- **Correctness — FRBR Subqueries:** Replaced `scalar_subquery()` (single-value context) with `.subquery()` in multi-row `IN(...)` filter chains inside `DataManager.get_stats()` to correctly communicate intent and avoid dialect edge-cases.
- **Collection page — URL sync:** Fixed trailing `?` appended to the URL when all filter/sort params are at their defaults (e.g. `/collection?` → `/collection`).
- **Collection page — Sort options:** Wired all 5 sort options end-to-end: "Recently updated" (default), "Recently added", "Title A-Z", "Title Z-A", and "Author". The `useItems` hook now passes `sort` to the API, and the backend's `GET /items` endpoint correctly handles each value.
- **Frontend JSDoc:** Added thorough JSDoc comments to all major frontend components, hooks, pages, and API utilities.
- **`Navbar` logout:** Added error handling to the logout flow and clears the React Query cache on sign-out.
- **Dockerfile:** Bumped base image to `python:3.14-slim`.
- **GitHub Actions quality workflow:** Updated branch targets, pinned Postgres image version, and adjusted artifact retention.
- **Markdownlint config:** Added `.pytest_cache` and `.agents/rules` to the markdownlint exclusion list (auto-generated/IDE files with non-standard formatting).

### Fixed

- **`Footer` JSDoc:** Corrected copy-paste error — JSDoc described the component as a "Sticky top navigation bar" instead of the site footer.
- **README code blocks:** Fixed four fenced code blocks in the Data Management section tagged as ` ```markdown ` (should be ` ```bash `), improving syntax highlighting.
- **README link:** Fixed broken "Installation Guide" link that pointed to a Google search URL instead of `docs/INSTALL.md#data-importexport`.
- **`get_alerts.sh` stderr redirect:** Fixed `2>&1 > .alerts.json` (stderr went to terminal) to `> .alerts.json 2>&1` (both streams captured in file).

### Database Migrations

No schema migrations are required for this release. The `unread` status is a new allowed value for the existing `Item.status` string column — no column type or constraint changes are needed.
