## Why

Multi-instance usability and SRE diagnostics between `preview.iqoqo.cc` and `peer.iqoqo.cc` revealed several UX and architectural friction points: (1) splitting peer trust into 4 levels (`untrusted`, `pending`, `trusted`, `blocked`) with a redundant `"Pending Review"` badge and jargon-heavy banner confuses administrators about how peer trust affects friend requests vs. catalog metadata; (2) `"Auto-Accept Follow Requests"` is misplaced as a global administrator setting rather than a per-user privacy preference; (3) the user menu `"Public Profile"` link leads to HTTP 404 when profile visibility is `private` or `friends_only`; (4) federated friend requests (`peer-admin@iqoqo.cc`, `peer-admin@iqoqo.cc@peer.iqoqo.cc`, `peeradmin@peer.iqoqo.cc`) fail or stall in `pending`/`queued` because `submit_task` does not catch Celery Redis result-backend `RuntimeError`s when `peer-web` lacks a worker/Redis and because `@` handle parsing splits on the first `@` instead of the last `@` without email fallback; and (5) `PUT /api/profile/` rejects `friends_only` for `visibility` and `default_item_visibility`. Consolidating these fixes in `v0.9.4` (`C89c`) delivers a self-explanatory 3-tier trust model, user-controlled follow auto-acceptance, resilient cross-instance friend delivery, and working `friends_only` profile settings.

## What Changes

- **Consolidate Peer Trust Levels into 3 Categories (`trusted`, `untrusted`, `blocked`) & Simplify Admin UI (`app/db/federation.py`, `app/core/federation_sync.py`, `app/core/federation_discovery.py`, `app/api/admin.py`, `app/api/federation.py`, `frontend/components/admin/federation-instances.tsx`, `frontend/components/admin/instance-settings.tsx`, `frontend/messages/en.json`, `frontend/messages/pl.json`)**:
  - Merge `pending` and `untrusted` into a single 3-tier model: **`trusted`** (auto-merges empty catalog metadata fields with provenance), **`untrusted`** (default for newly added peers; holds incoming catalog metadata in the Custodian Review Queue and requires manual or user-configured follow acceptance), and **`blocked`** (rejects all inbound ActivityPub requests and sync at the border). Normalize legacy `"pending"` values to `"untrusted"` in API responses and treat `"untrusted"` (and legacy `"pending"`) as review-queued in `sync_manifestation`.
  - Remove the redundant status badge/pill (`"Pending Review"` / `getTrustBadge`) next to the trust `<select>` dropdown in `federation-instances.tsx` so the dropdown is the single clear control per row.
  - Remove `FEDERATION_DEFAULT_TRUST` and `FEDERATION_AUTO_ACCEPT_FOLLOWS` from the Admin Federation Settings UI (`instance-settings.tsx`), since new peers always default to `untrusted` and follow auto-acceptance is now a per-user profile setting.
  - Rewrite the `/admin/federation` guidance banner in plain, everyday language explaining: (a) **One-way setup**: adding a peer here configures how *your* server treats incoming activity *from* that peer (the remote admin must also add your domain for two-way connection), and (b) **What the 3 Trust Levels do** (`Trusted`, `Untrusted`, `Blocked`) for friend requests, collection sharing, and catalog metadata.
- **Move Follow Auto-Acceptance to Per-User Profile Consent (`app/api/profile.py`, `app/core/federation_handlers.py`, `app/core/friend_service.py`, `frontend/components/settings/federation-consent.tsx`, `frontend/types/federation.ts`, `frontend/messages/en.json`, `frontend/messages/pl.json`)**:
  - Expose `auto_accept_follows: bool` (backed by `ConsentRecord` `consent_type="federation_auto_accept_follows"`, defaulting to `False` with zero schema migration required) in `GET /api/v1/profile/federation-consent` and `PUT/PATCH /api/v1/profile/federation-consent`.
  - Add an **"Auto-accept friend and follow requests"** toggle to `FederationConsentSettings` on `/profile` so each collector decides whether incoming friend/follow requests to their account are automatically accepted or held for manual approval.
  - Update `handle_follow` (`app/core/federation_handlers.py`) and local `send_friend_request` (`app/core/friend_service.py`) to evaluate the **target user's** `auto_accept_follows` preference (for any non-blocked peer instance or local user).
- **Remove Dead Navbar "Public Profile" Link & Forward Auth Cookies on `/u/[username]` (`frontend/components/dashboard/navbar.tsx`, `frontend/app/u/[username]/page.tsx`)**:
  - Remove the `"Public Profile"` link from the user avatar dropdown menu in `navbar.tsx` (which leads to 404 whenever a user's visibility is `private` or `friends_only`).
  - Forward the caller's request `cookie` header in `frontend/app/u/[username]/page.tsx` when fetching `/api/public/u/${username}` and `/api/public/u/${username}/items` (using `cache: "no-store"` when a session cookie is present) so authenticated owners and accepted friends can view `friends_only` profiles at `/u/<username>` without hitting an unauthenticated SSR 404.
- **Fix Federated Friend Request Delivery (`RuntimeError` Fallback) & Multi-Format `@` Handle / Email Resolution (`app/core/celery_app.py`, `app/core/tasks.py`, `docker-compose.federation-preview.yml`, `app/core/friend_service.py`, `app/api/federation.py`)**:
  - Configure fail-fast Redis transport retry bounds (`max_retries: 0`) on Celery broker/result backend in `app/core/celery_app.py`, catch `(KombuError, OSError, RuntimeError, Exception)` in `submit_task` (`app/core/tasks.py`) so unavailable Redis immediately returns `None` and triggers synchronous fallback (`process_inbound_activity` / `deliver_activity`) instead of throwing HTTP 500 after 20s, and set `CELERY_TASK_ALWAYS_EAGER=true` on `peer-web` in `docker-compose.federation-preview.yml` so the standalone peer container executes tasks against `peer-db` synchronously.
  - In `send_friend_request` (`app/core/friend_service.py`) and `_handle_webfinger_lookup` (`app/api/federation.py`), split federated handles from the **right** (`rsplit("@", 1)`) so email-based federated handles (`peer-admin@iqoqo.cc@peer.iqoqo.cc`) parse into `(identifier="peer-admin@iqoqo.cc", domain="peer.iqoqo.cc")`.
  - Allow WebFinger (`_handle_webfinger_lookup`) to resolve consented users by case-insensitive `public_username`, full `email`, or unique email local-part (when `public_username` is unset), and add fallback discovery across registered non-blocked `FederationInstance` peers in `send_friend_request` when a user enters a remote email (`peer-admin@iqoqo.cc`) whose mail domain differs from the peer host (`peer.iqoqo.cc`).
- **Fix `PUT /api/profile/` to Accept `friends_only` Visibility (`app/api/profile.py`)**:
  - Update `update_profile` (`PUT /api/profile/`) in `app/api/profile.py` to accept `["public", "friends_only", "shared", "private"]` for both `visibility` and `default_item_visibility`, matching `PATCH /api/profile/settings` and the `User` database `CheckConstraint`.

### Modified Capabilities
- `admin-federation-dashboard`: Consolidate peer trust selector into 3 levels (`trusted`, `untrusted`, `blocked`), remove the redundant status badge next to the dropdown, remove `FEDERATION_AUTO_ACCEPT_FOLLOWS` and `FEDERATION_DEFAULT_TRUST` from global admin settings UI, and replace the peering banner with a plain-language explanation of unilateral peering and the 3 trust levels.
